## 0. 扩展需求的设计衔接（2026-11-11）

选择：保留 [产品与三端架构讨论稿v0.4](BabyPlan-产品与三端架构讨论稿.md) 中记载的已确认需求，不将其视为废案。三端、父母协作、每天多项和成长档案尚未进入现有正式合同；新增 [三端原型简报](design/05-原型范围与三端简报.md)、[状态与文案](design/03-原型状态与文案清单.md)、[候选视觉基线](design/04-视觉与组件基线.md) 支持先做低保真。

理由：继续只按旧单安卓范围出图会漏掉已确认目标；直接改现有API又会把未评审交互误当成已确定规则。因此新N/W/C页面与P验收使用本地虚构数据，旧A/D页面、M阶段与OpenAPI留作旧基线验证；设计评审后统一升级规格、合同与校验，禁止混用。身份加入、自动生成、发布撤回、媒体隐私与参考曲线均按新简报标候选或待定。

本次新增的颜色、字号、间距与组件状态均为可替换设计候选，不表示用户已确认品牌。已有PNG保留为静态视觉提案，旧v0.1 ZIP为历史快照；最新输入包改用v0.2文件名，避免覆盖历史后仍被误读。

### 0.1 安卓低保真原型（2026-11-11）

选择：用本地静态 HTML/CSS/JS 先做安卓端可点击低保真（`prototype/mobile/`），数据由 `tools/build_mobile_prototype.py` 从扩展虚构样本生成；OpenDesign 与 Local Codex 暂不参与本轮。原型与源码随 v0.2 输入包交付。

理由：低保真要先验证信息层级、状态与流程，纯静态页面改动成本最低，也不需要先确认视觉风格或接入设计工具。原型只覆盖 N01—N12 与 24 个演示场景；网页家长区、内容管理区仍待后续轮次。

边界：保存、同步、冲突、上传、通知、身份均为页面内模拟，刷新即重置；不代表 Flutter App、APK、SQLite、系统通知或真实接口已实现。正式合同、Schema、OpenAPI 与旧 v0.1 包未改动；三段窗口、导航、记录粒度、成员角色、提醒时间、发布权限仍为候选，评审后统一升级。

### 0.2 网页家长区与管理区低保真（2026-11-11）

选择：按用户顺序补网页家长区W01—W08，再补内容管理区C01—C06。继续使用静态HTML/CSS/JS，两个目录分别为`prototype/parent/`、`prototype/admin/`，共用安卓端生成的虚构fixture。使用`prototype/index.html`作为总入口；本地服务增加`--surface all`，保留原安卓启动方式。

理由：在共享术语和样本下分别评审家长整理/打印与内容审核/发布，不把管理权限放进家长页面。周视图只展示样本已提供的日期，打印按内容选择，管理区采用样本候选权限矩阵。

边界：三端不共享修改后的状态；发布或撤回不改家庭页面。所有角色、连接、失败、冲突与版本切换均为内存模拟。正式合同与规格不改动；撤回对未开展项的影响、家庭新安排采用版本的时机、身份和真实权限仍待确认。验证结果以`prototype/验证记录.md`为准，打包通过不代表产品验收。

## 3. 已发现的差异及处理

| 差异 | 影响 | 当前采用的处理 |
| --- | --- | --- |
| 旧模板和新包都写 `schemaVersion: 1`，但旧的是 `days/activityId`，新的是 `cards/weekTemplates/cardIds` | 若只看版本号，会误用格式 | 旧模板归档；导入必须校验整个新合同，不能凭版本号接受旧结构 |
| 早期方案要求内置七张卡，当前框架改为服务端导入版本化内容 | 直接沿用旧方案会把业务内容写死在 App | 按当前框架通用渲染，保存计划快照 |
| 早期一周顺序以看图、滚球为主，当前首批正式计划是小手→小球→杯子→小手→袜子→小狗→小熊 | 容易把旧排周当作正式交付 | 正式包使用当前内容实施规范的六卡七天安排；演示包保留联调用途 |
| 内容原稿出现「换个时间试」，当前开发规范用三个具体跳过原因 | 前端标签与服务端枚举可能不一致 | 采用开发规范的 `family_busy`、`child_tired`、`time_unfit`；玩过可用 `want_again` |
| 原稿说新档缺内容时保留熟悉活动；新规范要求卡片适配目标档 | 可能把未标记适龄的旧卡排给新月龄 | 建议按卡片 `ageBands` 严格校验；跨档未提供内容时提示待补，不自动放宽适龄限制。该边界应在 M0 确认 |
| 文档约定七个固定档位，通用校验器只要求从 0 起连续、不重叠 | 合法 JSON 仍可能不符合首版固定档位约定 | 正式包制作和导入验收补查七档及 0～35 月边界；本次未修改 Schema 或校验逻辑 |

## 5. 内容工具实际覆盖什么

阅读脚本可确认：它检查 JSON Schema、重复 JSON 键、非法常量、集合 ID 重复、月龄连续性、卡片与模板引用、模板适龄性、可选内容字段与标签配对，以及正式渠道包名。

它不检查：活动是否适龄、材料是否安全、来源是否真实支持卡片、网络链接是否有效、卡片是否好懂、首批是否恰好六个主题、固定七档是否齐全，也不承担内容版本发布、回滚、鉴权和数据持久化。

校验脚本运行环境需要 Python 与 `jsonschema`。初次整理时受终端启动问题阻塞；2026-11-11已实际运行演示包校验通过（3张卡、2套模板）。新增OpenAPI与设计样本的检查范围另见交接包校验报告；结构检查不等于服务端或真机验收通过。

## 6. 建议维护方式

产品行为变更更新 `docs/specs/`；数据结构变更同步 Schema 和校验工具，必要时升级 `schemaVersion`；只改文案或活动内容时递增 `contentVersion`。历史方案继续留在归档目录，不与当前规范并列标记为「定稿」。

新决定记录日期、选择和理由；完成开发后把真实环境、接口合同与验收结果补入仓库。文档描述的目标和真实已实现能力应持续分开。
