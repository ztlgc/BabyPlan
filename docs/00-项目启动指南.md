# 新项目启动指南

> 2026-11-11范围说明：以下实施顺序保留v0.1单设备、一日一卡合同。当前用户先打磨扩展需求的三端设计，阅读 [设计输入入口](design/README.md) 与 [三端简报](design/05-原型范围与三端简报.md)；先完成低保真评审与合同升级，再据新版本安排实现。下文“第一项开发任务”不是本轮自动启动的任务。

整理日期：2026-11-10；设计准备与规格更新：2026-11-11。总体方向以「框架定稿」为依据；现已补齐 [设计交接入口](design/README.md)、[安卓交互](specs/03-安卓交互与状态规格.md)、[服务端数据与接口](specs/04-服务端数据与接口规格.md)、[OpenAPI](../contracts/openapi.yaml) 和 [验收规格](specs/05-实施阶段与验收规格.md)。这些是开发基线，尚非已实现能力。

## 1. 先明确要做成什么

BabyPlan 是供家长查看的家庭亲子活动工具。每天回答三个问题：今天怎么玩、玩完如何记、下周还想玩什么。活动在线下完成。

首版成功的判断是：家长能轻松看懂活动并连续使用，记录可靠、提醒合适，七天后能决定下周保留什么。打卡不能用于评价宝宝发育，也不以会几个单词、数字或动作评分。

| 范围 | 已有约定 |
| --- | --- |
| 使用对象 | 一个家庭、一台安卓手机；预置私人家庭凭证 |
| 内容范围 | 框架覆盖 0～35 月；首批正式内容只做 18～23 月 |
| 每天安排 | 一个主游戏；儿歌、英文、数感按卡片字段可选展示 |
| 主要页面 | 开始计划、今天、本周与历史回顾、设置 |
| 技术方案 | Flutter、Fastify + TypeScript、PostgreSQL；手机使用 SQLite |
| 数据原则 | 保存计划和打卡；月龄在手机本地；不需要姓名、生日、照片或录音 |
| 首版建议 | 周报由程序计算，AI 在基础流程稳定后接入；家长确认才改变下周计划 |

公开注册、多家庭、多设备、课程商城、内容管理后台、音视频播放和完整 0～3 岁内容库均不纳入当前首版。

## 2. 现在有什么，还缺什么

已具备：三份当前规范、六个主题的内容原稿、JSON Schema、演示包、Python 校验脚本。演示包包含 3 张活动卡和 18～23、24～35 月两套模板；后一套用于联调，不表示正式内容已覆盖 24～35 月。

尚缺：正式 `release` 内容包、实际设计稿及其审阅、数据库迁移、App 与服务端代码、安卓真机验证、家庭试用结果。页面状态、OpenAPI、数据与错误规则已补为v0.1规格，见本文件开头链接。引用资料链接尚未逐一联网核实。

结论：产品范围足够启动第一轮实现，但现有资料还不是可直接安装的项目。下一步应围绕第一个可验收流程补少量约定并实现。

## 3. 下一步先做什么

**第一项开发任务：用演示包跑通安卓真机的最小完整流程。**

目标路径：导入演示包 → 选 18～23 月模板 → 从本地当天开始七天计划 → 手机查看当天活动 → 锁屏提醒并点开对应卡 → 记录「一起玩了 / 今天跳过」→ 重开后从服务端读回。

开工时按以下顺序处理：

1. 确认目标安卓机与版本、是否有可用的 Mac/Windows 开发电脑、Flutter/Android SDK、Node.js 和 PostgreSQL。开发电脑与手机先在同一网络联调。
2. 初始化 Git 仓库；当前目录尚未建立 Git。添加 Flutter、Node.js 和本地配置的忽略规则，配置示例中只放占位值。
3. 按现有OpenAPI与数据规格建立接口实现和迁移，核对请求字段、响应、归属、错误码与重复请求处理。
4. 将设计简报和样本交给OpenDesign Cloud或Local Codex，先审阅低保真流程和状态，再细化视觉；按安卓03与验收05核对产物。
5. 建最小服务端和数据库，导入演示包；Flutter 通用渲染卡片，接真实接口；接入安卓本地提醒并真机验收。

建议目录：`apps/mobile/`、`services/api/`、`contracts/`、`content/`、`tools/`、`docs/`。先保持一个仓库，不引入首版用不到的部署平台或管理后台。

正式内容制作可同时推进：把六张母卡转成 `family-play-zh-cn-v1.json`，补齐每张卡的四类回应、步骤、材料、安全说明和来源，安排七天模板并做人工试玩。内容制作不阻塞演示包联调。

## 4. 按验收结果分阶段

以下是实施建议，沿用原开发规范的先后关系。未确认团队投入和开发环境前，不承诺固定工期。

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| M0：开工准备 | 仓库、开发说明、最小接口合同、页面状态、内容校验入口 | 开发者能准备环境，双方对同一份演示数据和接口联调 |
| M1：真机完整流程 | 内容导入、建周、看卡、提醒、在线打卡与读回 | 真机锁屏收到通知，点开正确卡；重开能读回；重试没有多条有效结果 |
| M2：连续使用 | SQLite 缓存、待同步队列、补记改记、提醒重排、基础周报 | 断网重开记录仍在；恢复网络按顺序同步；未来日期不算未记录；已打卡取消提醒 |
| M3：内容发布与试用 | 版本切换、快照隔离、正式 18～23 月包、家庭连续试用 | 同一 APK 新周显示新版台词，旧周保持原话；坏包拒绝；正式包通过校验及人工审阅 |
| M4：AI 与下周调整 | 手动生成有依据的建议、确认后换下周一天 | 两次偏好、少量记录、全未记录、模型失败均有合理结果；不改旧周、不重复建周 |

每阶段通过后再进入下一阶段。M1 不要求完成离线队列或 AI，但应预留稳定任务 ID、操作 ID 和卡片快照，避免 M2 重做数据模型。

## 5. 数据和接口先守住的规则

- 内容、计划、记录分开：内容有版本，排周时保存卡片快照；更新内容不重写旧计划。
- 每个家庭每天最多一项任务；七天是从选定开始日连续计算，不默认等于自然周。
- 任务日期、实际操作时间、同步时间分开；补记归原任务日期，未来任务不计入未记录。
- 建周按 `requestId` 幂等；打卡按 `operationId` 去重。同一任务的修改顺序必须明确，旧响应不能覆盖本机新修改。
- Schema 校验后还需业务校验。包版本冲突、模板引用、月龄适配、日期重叠和归属检查不能只依赖字段类型。
- 演示数据与家庭真实数据分开；家庭试用前落实私人访问、加密传输与备份恢复步骤。

## 6. 家庭试用时观察什么

建议先试用七天，记录三个问题即可：家长看卡是否立刻知道怎么玩；记录或提醒是否造成负担；哪些活动确实想再玩。再核对补记、断网和改提醒时间是否可靠。

是否进入下一轮开发，根据试用问题决定。若看卡和记录都不顺畅，应先改这一条路径；若基础流程已可靠，再判断 AI 建议是否值得加入。
